# 输出契约 v1.0

## 1. 人读版先行
创意卡、大纲和剧本正文采用中文 Markdown；机器需要的字段用 JSON。二者共享集号、场景 ID 和 canon 版本。模板在 `templates/`，JSON Schema 在 `schemas/`。

所有 JSON 必须可解析，不能含注释、尾逗号或省略号。未知值用 `null` 并解释，不伪造精确数字。模板中的空串、空数组或“待填写”不可标成成品。

## 2. 概念卡
`concepts.json` 为数组；每项必须含：
`id, title, logline, primary_pleasure, protagonist_goal, mechanism_summary, first_payoff, unique_scene, serial_engine, risk, fingerprint, variant_of`。

`fingerprint` 为对象，九个键各为非空字符串数组：
`desire, advantage, operation, obstacle, relationship, reveal, reward, growth, arena`。

卡片不是作品完整稿。`variant_of` 为 `null` 或上游概念 ID。`compare` 只用于提醒近似。

## 3. Episode JSON
顶部：`schema_version, project_id, episode_id, episode_number, title, language, status, target_duration_seconds, duration_seconds, timing_status`。

`status`: `draft` 或 `accepted`；`timing_status`: `estimated` 或 `measured`。后者只有真实配音/成片测量后可用，并应在项目日志记录来源。

资产表：`characters, locations, props` 均为 `{id,name}` 数组；`rules_used` 为规则 ID 数组。资产在 bible 中定义，episode 只列本集实际涉及资产；`props` 允许空数组。

`scenes` 每项含：
- `id, location_id, character_ids, prop_ids`。
- `start_seconds, end_seconds`：集内连续时间轴，不重叠，不隐性留空。
- `goal, obstacle, action, turn, state_out`：允许无恶人，但要描述有效变化。
- `non_overlapping_action_seconds`：对白之外必须占用的时间。
- `dialogue`：`{speaker_id,text,kind}` 数组；kind 为 `spoken/voiceover/inner/system`。旁白 `NARRATOR`、系统 `SYSTEM` 为保留声源，无需人物资产；其他 speaker 必须在角色表，画外音不要求在场。
- `on_screen_text`：准确字幕文本数组；可为空。

`payoffs` 至少一项：`id,kind,scene_id,promise,visible_evidence,state_change`。悬疑进展、关系选择、安心和喜剧满足均可作为回报，但不能填“本集很爽”。

`ending`：`type,question,planned_resolution_episode,cause_scene_id,is_finale`。完结可用 `type=closure`、空 question、null resolution；非完结钩子的计划兑现集必须晚于当前集。

`continuity`：
- `requires`: 所依赖的已知事实 ID 数组。
- `establishes`: `{id,text,known_by,source_scene_id}` 数组。
- `state_changes`: `{entity_id,field,before,after,cause_scene_id}` 数组。
- `promises`: `{id,description,opened_episode,due_episode,status,resolved_episode,evidence_scene_id}` 数组。status 为 `open/partial/resolved`；回收必须附证据。

`production_handoff`：`critical_visuals`（scene_id + must_show）、`continuity_locks`、`complexity_risks`、`camera_status`。不虚构已完成分镜，默认 `not_planned`。

`review`：`status,hard_failures,scores,open_issues`。scores 的条目为 `criterion,score,evidence_scene_ids,reason`，十种 criterion 见 08。未审稿可为 `not_reviewed` 和空 scores。accepted 必须通过硬门槛、分数门槛且正文 status 同步。该状态是项目编辑接受，不是市场验证或官方认证。

## 4. 项目文件
`brief.json`：用户约束、默认假设、交付范围和生成参数。
`bible.json`：稳定角色、地点、道具、规则、初始事实和锁定项。
`series-plan.json`：集数、阶段、分集卡、终局兑现。
`project-state.json`：项目 ID、版本、计划总集数、完成集号、已接受正文路径、草稿路径、状态账本、承诺、摘要、下一步。

已接受正文路径登记在 `episode_files`，相对项目根，例如 `episodes/EP01.json`。`completed_episodes` 使用 `EP01` 字符串；不能把草稿路径算作完成。

命令 `check-project` 检查基础文件、已登记正文、资产/规则引用、初始事实与逐集事实依赖、连续 state_changes 的前后值，并提醒逾期承诺。只检查编码进字段的事实；自然语言中的隐含矛盾仍需审稿。

## 5. schema 与命令的边界
JSON Schema 描述数据类型、必填字段和枚举；附带 Python 工具对关键结构及跨字段约束做检查，不是通用 JSON Schema 解释器。Schema 合法也不能自动判断语义正确、原创或好看。

用户只要正文时不强迫聊天显示所有字段；项目工作流仍可把结构化副本写入文件。没有文件权限时输出文本，不宣称已经持久保存。

## 6. 可选 Reveal Arc JSON（v1.0 独立扩展）

详细 schema：`schemas/reveal-arc.schema.json`；模板：`templates/reveal-arc.json`；完整示范：`examples/reveal-arc.json`。本扩展不改变 episode v1.0 必填字段；按需保存在项目 `reveal-arcs/`。空模板不是有效成稿。

顶层：`arc_id,title,mode,status,start_episode,due_episode,setback_budget,core_truth,audience_anchor,protagonist_goal,why_not_reveal_immediately,actors,facts,beats,final_cashout,next_conflict`，以及 `schema_version=1.0`。status 的 planned 是设计方案，in_progress 是部分执行，resolved 是已写完且在正文实际结算；示例保持 planned，不假装已经拍摄或做过市场验证。

`actors` 保存 initial_belief / initial_stance / incentive，剧中群众使用稳定角色或群体 ID。`facts` 是可信的“可观察信息”，反派谎话只能记为“某人声称了 X”，不能直接把 X 当作真实世界事实；`introduced_at_beat` 指首次可引用的节点。

每个 beat 记录集数、场景、类型、争议问题、观众期待、新信息、证据 ID、主角动作、belief_updates、public_moves、earned_payoffs、carry_forward_payoff_ids 和 setback_reason。内心判断与公开表态独立更新；每次更新的 before 要与该人物上一状态相同。

carry_forward_payoff_ids 列出所有此前已获得且仍保留的回报，不含本节点才新获得的回报。本检查器面向“保留已兑现回报”的揭晓弧；确有合理失去成果的其他剧情应另建弧并做语义审稿，不将其伪填为保留。

final_cashout 用具体证据、实际变化和 old_question_closed 指定结算；其场景必须在 beats 内，事实不能来自更晚节点。resolved 弧要求旧问题已关闭、结算节点有实际回报；planned 可以还没执行，但设计也需完整。

`check-reveal` 是独立命令，`check-project` 不会自动扫描 reveal-arcs。跨集事实、场景与正文的一致性仍要对照 episode 与 bible 人工/模型审读。不存在已跑过模型测试或证明观众偏好的隐含结论。

brief v1.0 另支持可选 `narrative_controls` 对象；具体枚举见 brief schema，默认值在模板中。它是兼容的可选扩展，不要求旧项目补填才能通过校验。
