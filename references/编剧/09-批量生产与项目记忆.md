# 09｜批量生产与项目记忆

批量目标是“获得更多差异明显且有发展价值的候选”，不是制造无限字数。Skill 本身不是调度器，不会自动在后台运行，也不包含模型 API 调用。

## 1. 两阶段漏斗
**低成本发散**：先写短卡，每卡约一小段，记录核心机制和代表场面。没有验证引擎之前不为 30 个候选都写完整世界观。

**高质量开发**：比较差异、修掉根本风险，再为少数候选开发人物、规则、长篇架构和正文。

默认 12→3→1；用户要求 100 个时，分批 10–20 张并持久化，尽量保持同等信息密度。不要把“给 100 部成稿”悄悄缩成 100 个标题。若一次执行无法完成，报告真实完成范围和文件，不声称余下正在后台进行。

## 2. 多样性不是随机词语拼接
维护覆盖表：主满足感、冲突机制、优势来源、主角关系结构、成长方式、认可渠道、结尾类型、时代/场景、基调。

用户无题材约束时，默认一批不要让任一单一“优势机制+制胜方式”组合占比过高，目标不超过约三分之一；这是编辑筛选起点，不是统计结论。用户只要同一类型时，在方法和关系层做差异，不能为满足配额偏离需求。

保留低占比探索位，例如无外挂、无羞辱、无反派、无榜单的创意；没有要求这些元素必须禁用。

## 3. 机制指纹
每张卡使用统一字段与可复用短标签：
`desire / advantage / operation / obstacle / relationship / reveal / reward / growth / arena`。

标签描述因果，不是堆专有名词。例：`operation: [恢复历史功能, 可逆试验]`，比 `[神级秘术, 超级法宝]` 更有用。批次中统一同义词，例如“专家认可”与“专业承认”先归一，避免工具漏检。

另写 `mechanism_summary`，用两句话说明如何产生冲突与结果。`variant_of` 标注主动变体、续作或同机制实验，不把它们伪装成完全独立新剧。

工具只做标签重合和措辞近似；真正的语义去重仍需比较完整卡片。相似分值不等于抄袭概率。

## 4. 项目文件
```text
project/
  brief.json
  bible.json
  series-plan.json
  project-state.json
  archive.jsonl
  concepts/
  episodes/EP01.md
  episodes/EP01.json
  reviews/EP01-review.md
  handoff/
  run-log.md
```

`bible` 保存锁定设定；`series-plan` 保存阶段和分集意图；`project-state` 保存当前事实、完成范围和下一步；`archive` 保存候选指纹。不要把每轮完整输出重新塞进一个越来越大的文件。

## 5. 安全续写与回滚
使用单一写入者更新 canon；其他审稿者只提交建议。每次保存先检查 JSON 可解析、ID 一致、关联文件存在，再更新索引。

修改已批准设定：记录旧值、新值、理由、受影响集数；同步修复相关正文与账本，不静默覆盖。必要时保留旧版，不删除用户原稿。

断点文件明确：正在开发的项目、已 accepted 的集数、草稿集数、最后完整文件、失败检查、下一步。恢复时先读取它，不能从头重造剧本。

## 6. 档案写入
`archive` 命令仅在明确给出输入与本地档案路径时执行。它检查重复 ID，使用锁和原子替换；不会删除旧记录，也不会自动上传。并发锁残留时先确认无其他进程，不盲删。

跨项目查重只访问用户提供的档案，不搜私人无关文件。不存在的历史不能假装已经检查。

## 7. 运行预算
开始记录：用户要求数量、本批数量、最大修订轮次、输出目录、完成定义。没有预算时默认两轮修订，并且只为筛选出的少数候选写长正文。

不执行无限递归“直到完美”；不为自评分多 1 分持续调用模型；不将“疯狂生成”理解为不经授权的收费、自动发布或持续后台运行。

## 追加｜反转链也需要去重

批量比较“谁误判什么→拿什么反证→群众如何转向→主角如何证明→怎样结算”。仅把鉴宝大会换成公司会议、把证件换成令牌，不算机制不同。记录已经使用的揭晓阶梯与群众动作，允许风格复现但须改变疑点、行动与结果。`compare` 无法自动理解这些语义，须另做编辑检查。
